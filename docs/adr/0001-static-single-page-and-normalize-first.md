# 静态单页、归一化先行、扁平服务注册表

本工具只做字符串变换：把一个 GitHub 源地址变成多个加速地址。整个领域里没有任何需要服务端的状态——不需要数据库、不需要鉴权、不需要跨用户的统计，也不需要缓存文件。因此产品形态定为**纯静态单页**，逻辑全部跑在浏览器里，产物是一个可 `file://` 直接打开的自包含 HTML，同时可发布到 GitHub Pages。

选择静态带来的直接代价是无法做服务端探活。但我们实测发现浏览器端探活本身就是有害信号：ghproxylist.com 用前端 `fetch` 检测代理，把它自己列表里 5 个服务**全部标为「离线」**，而其中 3 个在 `curl` 下返回 200——跨域限制把可用服务判成了不可用。所以「不做探活、只给复制与打开」不是妥协，而是唯一诚实的做法：让用户自己点一下，比给一个会骗人的绿点更好。

数据流被固定为**归一化先行**：任何源地址先解析成 `{owner, repo, ref, path}` 四元组或 `{user, gistId}`，能落到直链的（仓库单文件、gist）重建为直链，再交给各加速服务；release 资产与归档包没有直链形态，则以原地址透传给前缀拼接式服务，路径重排式服务对它们无处可放。这条次序是硬约束，因为实测发现上游服务的实现质量参差：`ghproxy.xyz`、`gh.monlor.com` 会把 `github.com/o/r/raw/main/f` 错转成 jsDelivr 的 `/raw/main/` 路径并返回 404，`github.chenc.dev` 则会把 `blob` 浏览页原样当 HTML 返回，而先归一化成 `raw.githubusercontent.com/o/r/main/f` 再拼接就绕过了这两类缺陷。若让每个服务各自解析源地址，就等于把每个上游的 bug 都复刻一遍。

服务注册表保持**扁平**：一个服务一条记录，带端点与地址语法两个字段。我们明确放弃了「语法家族 → 成员」的树形抽象——尽管 `cdn.jsdelivr.net` 与 `cdn.jsdmirror.cn` 的路径语法完全相同、看起来适合归为一族。放弃的理由是：家族层只服务于「减少重复配置」，而重复配置的规模只有十几个字符串；它却会让 UI 出现分组折叠，破坏「有几条源地址就出几组、每组都是完整列表」的可预期性。共享构造器可以存在于代码里，但不应上升为数据模型与界面结构。

## 影响

- 新增一个加速服务 = 在注册表里加一条数据，不改任何逻辑。
- 地址语法的种类一旦要增加第三种（例如 `?q=` 查询参数式），必须改构造器，不能只加数据；`ghfast.top/?q=` 已确认只是重定向糖，不需要引入。
- 所有正确性风险集中在归一化与两个构造器上，单元测试必须覆盖这两处。
